# 記事トンマナ＆SEOレビューツール ＋ 日報自動生成

Claude Codeを使った半自動の業務効率化ツール群です。

1. **記事レビュー＆自動修正**（トンマナ/SEO）
2. **ファクトチェック**（記事の信頼性チェック）
3. **日報自動生成**（今日のタスクを書くだけで所感まで作成）

## ディレクトリ構成

```
hibikiclaude/
├── config/
│   ├── brand-rules.yaml            # ブランドルール設定（一度設定すればOK）
│   └── daily-report-config.yaml    # 日報のKPI・カテゴリ設定（月初に更新）
├── input/
│   ├── article.md                  # 記事入力用（都度編集）
│   └── daily-tasks.md              # 今日のタスク入力用（毎日編集）
├── data/
│   └── kpi-log.md                  # 日次実績台帳（自動追記）
├── output/
│   ├── article-fixed.html          # 修正済みコード出力先
│   └── daily-report-YYYY-MM-DD.md  # 日報出力先
├── templates/
│   ├── review-prompt.md            # レビュー出力形式の定義
│   ├── auto-fix-rules.md           # 自動修正ルール
│   ├── fact-check-prompt.md        # ファクトチェック出力形式
│   ├── fact-check-fix-rules.md     # ファクトチェック修正ルール
│   ├── daily-report-prompt.md      # 日報の出力形式・生成手順
│   └── insight-rules.md            # 所感・課題・翌日タスクの生成ルール
└── README.md
```

## 機能一覧

| コマンド | 機能 |
|----------|------|
| `レビューして` | トンマナ/SEOチェック＆修正案提示 |
| `レビューして修正まで` | レビュー＋自動修正＋HTML出力 |
| `修正だけして` | レビュー省略で修正済みHTML出力 |
| `ファクトチェックして` | 要検証主張の抽出＆チェック計画作成 |
| `ファクトチェックして修正まで` | ファクトチェック＋自動修正＋HTML出力 |
| `日報作って` | タスク入力から日報を生成＋台帳へ追記 |
| `日報の下書きだけ` | 画面表示のみ（ファイル出力なし） |
| `所感だけ書いて` | 所感セクションのみ生成 |
| `今週の稼働割合出して` | 台帳から週次稼働割合を集計 |

## 使い方

### STEP 1: ブランドルールを設定（初回のみ）

`config/brand-rules.yaml` を開き、以下を設定：

- 口調（ですます/だである）
- トーン（丁寧/カジュアルなど）
- 禁止表現・禁止ワード
- 文字作法（半角全角ルール）
- SEO要件

### STEP 2: 記事と情報を入力（都度）

`input/article.md` を開き、以下を入力：

1. **記事情報**（表形式）
   - 目的
   - ターゲットKW
   - 二次KW
   - 競合差分

2. **記事本文**
   - コードブロック内に貼り付け

### STEP 3: レビュー＆修正を実行

#### レビューのみ
```
レビューして
```

#### レビュー＋自動修正＋HTML出力（推奨）
```
レビューして修正まで
```

### STEP 4: 結果を受け取る

**レビュー結果**:
1. 総評（200字以内）
2. トンマナ逸脱リスト（表形式）
3. 読みやすさ改善（箇条書き）
4. SEO改善（箇条書き）
5. 重要度タグ（A/B/C）
6. 修正後サンプル文章（3箇所）

**修正済みHTML**:
- `output/article-fixed.html` に出力
- 修正ログも併せて表示

## 自動修正の対象

### 重要度A（必須修正）- 自動対応
| 項目 | 内容 |
|------|------|
| カギ括弧削除 | 「」を全て削除 |
| 問いかけ修正 | 〜ませんか？→平叙文に変換 |
| HTML構文修正 | 閉じタグ漏れ等を修正 |

### 重要度B（推奨）- 自動対応
| 項目 | 内容 |
|------|------|
| 長文分割 | 80字超の文を分割検討 |
| 表記統一 | brand-rules.yaml に従い統一 |

### 手動対応が必要
- SEO関連（タイトル、KW配置）
- コンテンツの追加・削除
- 画像alt属性の設定

## カスタマイズ

### 禁止ワードを追加する

`config/brand-rules.yaml` の `prohibited.words` に追加：

```yaml
prohibited:
  words:
    - "絶対"
    - "必ず"
    - "誰でも簡単に"
```

### 用語統一を設定する

`config/brand-rules.yaml` の `writing_rules.terms` に追加：

```yaml
writing_rules:
  terms:
    SEO: "seo, Seo"
    Webサイト: "WEBサイト, webサイト"
```

## ファクトチェック機能

### 概要

記事内の「検証が必要な主張」を自動抽出し、チェック計画を作成します。
数値、統計、法律、医療など、誤りがあると信頼性を損なう情報を重点的にチェックします。

### 使い方

#### STEP 1: 記事を入力
`input/article.md` に記事本文を貼り付け

#### STEP 2: ファクトチェック実行
```
ファクトチェックして
```

#### STEP 3: 結果を確認

**出力内容**:
1. リスク評価の総評（100〜200字）
2. 要検証リスト（表形式）
3. 断定回避テンプレ（5つ）
4. 最優先確認リスト（上位5件）

#### STEP 4: 修正まで実行（オプション）
```
ファクトチェックして修正まで
```

### ファクトチェック出力サンプル

```
## 1) リスク評価の総評
本記事には12件の検証が必要な主張が含まれています。
特に数値データ（5件）と法律関連（2件）はリスクが高く、
公式出典での確認が必須です。医療効果に関する記述は
表現の緩和を推奨します。

## 2) 要検証リスト
| # | 主張 | 種類 | リスク | 理由 | 検証方針 | 推奨出典 | 修正案 |
|---|------|------|--------|------|---------|---------|--------|
| 1 | 利用者数は1億人を突破 | 数値 | 高 | 出典不明 | 公式発表を確認 | 企業IR/プレスリリース | 約1億人以上とされています |
| 2 | 業界シェア1位 | 統計 | 高 | 比較時点不明 | 調査会社データを確認 | 矢野経済研究所等 | 主要なサービスの一つ |

## 3) 断定回避テンプレ
- 〜とされています
- 〜と言われています
- 〜という報告があります
- 一般的に〜と考えられています
- 〜の傾向が見られます

## 4) 最優先確認リスト
1. 利用者数は1億人を突破（数値/高）- 法的リスク回避のため
2. 業界シェア1位（統計/高）- 景表法違反リスク
3. ...
```

### チェック対象の種類

| 種類 | 説明 | リスク基準 |
|------|------|-----------|
| 数値 | 具体的な数字、金額、% | 出典不明なら高 |
| 統計 | 調査結果、ランキング | 時点・母数不明なら高 |
| 法律 | 法令、規制、罰則 | 常に高（専門家確認推奨） |
| 医療 | 健康効果、治療法 | 常に高（薬機法注意） |
| 比較 | 最も〜、唯一〜、1位 | 根拠不明なら高 |
| 因果 | 〜すると〜になる | 断定表現なら中〜高 |

### 自動修正の対象

**自動修正する**:
- 未検証の断定表現 → 推量・伝聞表現に緩和
- 最上級・絶対表現 → 限定的な表現に緩和
- 出典不明の数値 → 「約」「程度」を追加

**手動確認を推奨**:
- 法律・規制関連
- 医療・健康関連
- 企業・製品の固有情報
- 人物の経歴・発言

## 日報自動生成機能

### 概要

**今日やったタスクと時間を書くだけ**で、所感・課題・翌日タスクまで揃った日報を生成します。
過去の実績は `data/kpi-log.md` に蓄積されるため、KPI進捗と週次稼働割合は必要になったときにいつでも集計できます。

### 使い方

#### STEP 1: KPIとカテゴリを設定（初回＋月初のみ）

`config/daily-report-config.yaml` を開き、以下を設定：

- 月間KPI（架電数、アポ件数など）と当月の営業日数
- 業務領域カテゴリ（週次稼働割合の集計軸）
- 目安とする稼働割合
- 文体・所感の方針

#### STEP 2: 今日のタスクを書く（毎日）

`input/daily-tasks.md` に記入します。上長フィードバック（2026-09）を受け、
**タスク名とアウトプット（件数・決定事項）が必須**になりました。

```markdown
| タスク名（何の・何のためか分かる形で） | 時間(h) | アウトプット・件数・決定事項 |
|----------------------------------------|---------|--------------------------------|
| 架電業務（比較サイト経由リード） | 4.0 | 32件架電、アポ1件。不在が多い |
| クライアントMTG（営業AX Web戦略） | 1.5 | カニバリ解消を最優先方針に決定。議事録はチームドライブ参照 |
| クライアント向けロードマップ資料作成 | 3.0 | 全5章中3章完成、残りは明日 |
```

**タスク名は「MTG」「対応」だけで終わらせない**（何の・何のためかを入れる）、
**MTGは目的とそこで決まったことを書く**、**物量は数字で示す**の3点が今回のポイントです。

#### STEP 3: 日報を生成

```
日報作って
```

#### STEP 4: 結果を受け取る

- `output/daily-report-YYYY-MM-DD.md` にコピペできる形で出力
- `data/kpi-log.md` に本日分が自動追記され、翌日以降の集計に反映

### 出力サンプル

標準では次の5セクションを出力します（実例：`output/daily-report-2026-08-26.md`）。

```
■週次の稼働割合
・EmmaQuickリリース業務（6.0h）
・クライアントタスク（4.0h）
・社内MTG（3.5h）
・クライアントMTG（2.0h）
・メール対応・事務（0.5h）

■本日の業務実績
・EmmaQuick新規リリースNotion作成（3.5h）：新機能3件分のリリースノートを作成、公開待ち
・Emmaクライアント競合洗い出し（2.0h）：競合5社を抽出しリストをチームドライブへ格納
・社内MTG（クライアント向けロードマップ作成の進め方すり合わせ）（1.0h）：
  3フェーズでパターン分けする方針に決定

■所感
吉田さんとの社内MTGで、クライアント向けロードマップ作成の進め方を擦り合わせました。
コンサル側ではGA4やサーチコンソールのAPIを繋いだ分析の自動化がすでに進んでおり、
...

■課題・相談事項
特になし

■次の営業日（8月27日）のタスク
・クライアントのサイト分析（3.5h）
・EmmaTools機能紹介ページの改修（3.0h）
```

### 週次の稼働割合について

- 集計期間は**火曜起点**（`weekly_ratio.week_start` で変更可）から本日まで
- 個別タスクではなく、`weekly_groups` の**グループ単位で大まかに束ねて**合算します
  - EmmaQuickリリース対応 ＋ Notion作成 ＋ フルスタ作成 → EmmaQuickリリース業務（6.0h）
  - クライアントMTG ＋ その準備 → クライアントMTG（2.0h）
- 表示は時間（h）のみ。%を併記したい場合は `weekly_ratio.unit` を `percent` に変更
- 新しい業務が増えたら `weekly_groups` にグループを追加してください

### 出力セクションの切り替え

`config/daily-report-config.yaml` の `sections` で、セクションごとに出力の有無を切り替えます。

| セクション | 標準 |
|------------|------|
| ■週次の稼働割合 | 出力する（火曜起点、グループ別の時間） |
| ■本日の業務実績 | 出力する（具体的なタスク名＋アウトプット・件数・決定事項） |
| ■所感 | 出力する |
| ■課題・相談事項 | 出力する（課題・相談・連絡事項のいずれでもOK。なければ特になし） |
| ■次の営業日のタスク | 出力する（タスク名と時間のみ） |
| ■担当KPIと進捗 | 出力しない |

### 本日の業務実績の3原則（上長フィードバック反映：2026-09〜）

上長から「何のタスクか分からない」「MTGの中身が分からない」「物量が分からない」という
フィードバックを受け、`work_log` のルールを次のように変更しました。

| 原則 | 悪い例 | 良い例 |
|------|--------|--------|
| ①タスク名を具体的に | MTG（4.0h） | クライアントMTG（営業AX Web戦略）（1.5h） |
| ②MTGは目的・決定事項を書く | クライアントMTG（1.5h） | クライアントMTG（営業AX Web戦略）（1.5h）：カニバリ解消を最優先方針に決定 |
| ③物量は数字で示す | 架電業務（4.0h） | 架電業務（4.0h）：32件架電、アポ1件 |

議事録などの詳細情報はチームドライブに格納し、日報には要点のみ書きます
（`work_log.mtg_rules.detail_location` で参照先の書き方を定義）。
詳細は `config/daily-report-config.yaml` の `work_log` と、
`templates/daily-report-prompt.md` の「■本日の業務実績」欄を参照してください。

### 所感の書き方ルール

`templates/insight-rules.md` に定義しています。所感は必ず次の3段構成で生成されます。

| 段 | 内容 |
|----|------|
| ①事実 | 今日何を見て、何に気づいたか |
| ②解釈 | そこから何が言えるか（分類・仮説・原因） |
| ③打ち手 | 明日以降どう動くか（誰に・何を・どうする） |

- テーマは**1つに絞る**（全タスクを羅列しない）
- 打ち手には**相手と行動**を必ず入れる
- 頑張ります等の精神論、根拠のない一般論は出力しない

### 台帳の運用

`data/kpi-log.md` は1タスク＝1行で蓄積されます。

- **週明け**：先週分の明細を「アーカイブ」へ移し、日次明細の見出しの日付を更新する
- **月初**：累計を0にリセットし、`daily-report-config.yaml` の `kpi.month` と `business_days` を更新する

### 事実の創作を防ぐ仕組み

入力にない数字・出来事・発言は書きません。

| 種別 | 扱い |
|------|------|
| 入力にある事実 | そのまま記載 |
| 事実からの解釈 | 〜と感じました／〜と考えます で記載 |
| 入力にない数字 | 記載しない（KPI未入力は「未入力」と明記） |
